07 / Governance

Rules that keep Diarito consistent.

This consolidates the useful rules from the original Diarito library with the decisions fixed during the 2.x rebuild.

Master rules

The library is the visual source of truth. Screens compose it; they do not quietly fork it.

01 · General principle

  • Diarito should feel light, friendly, clear, contemporary and consistent.
  • Reuse an existing component before creating a new variant.
  • Reusable classes use the .diarito-* namespace.
  • Generic UI stays neutral; brand colors remain available as tokens, not decoration.

02 · Component governance

  • If a shared component exists, a screen does not recreate its radius, height, color, border or hover behavior.
  • New reusable variants are added to the library first, then consumed by screens.
  • Page CSS may arrange components; it may not redefine their visual internals.

03 · Tokens & themes

  • New colors, spacing, radii, shadows and z-index values become tokens before component literals.
  • Light is the default theme. Dark and future themes override semantic roles instead of component CSS.
  • The library does not force OS-theme detection or persistence.

04 · Typography

  • Roboto and Noto Sans KR are the operational UI pair.
  • Englebert and Poor Story are display fonts for short expressive moments, not forms, tables or long body text.
  • Labels stay visible; placeholders never replace labels.

05 · Color & semantic states

  • Success, warning, error and info use Tailwind 500 as their semantic base.
  • State text uses Tailwind 700 in light mode and contrast-safe semantic text roles in dark mode.
  • Important meaning never depends on color alone.
  • Do not introduce isolated hex values when a semantic token exists.

06 · Layout & spacing

  • Pages use .diarito-section + .diarito-container as the page-level contract.
  • Peer sections share the same max-width unless a deliberate reading-width pattern says otherwise.
  • Spacing comes from the shared scale.
  • Editorial/product documentation favors one central scrolling column over dashboard fragmentation.

07 · Borders, radius & shadows

  • Cards, tables, form controls and overlays may use structural 1px borders.
  • Buttons, badges, tags, alerts, tabs and pagination remain borderless.
  • No border-left-only state accents.
  • Use the shared sharper radius scale.
  • Shadows are subtle and compact; no large spaced/blurred decorative shadows.

08 · Cards & surfaces

  • Cards use semantic surfaces, structural borders and shared radius tokens.
  • Cards do not clip overlays by default; use .diarito-card--clip only when content genuinely needs clipping.
  • Header/body/footer separators are structural, not decoration.

09 · Buttons & actions

  • Small is the default button size; medium and large are opt-in.
  • Buttons use no border and do not jump on hover.
  • Icon-only buttons require an accessible label.

10 · Forms

  • Inputs, selects and textareas use a semantic surface, neutral 1px border and visible focus state.
  • Form controls stay medium-height even though buttons default small.
  • Desktop forms may use columns; mobile collapses them when needed.
  • Autocomplete/searchable fields keep real IDs separate from visible labels when applicable.

11 · Navigation, tabs & accordion

  • Tabs have normal and selected states; avoid decorative hover choreography.
  • Scrollable tab rows hide their native scrollbar while remaining scrollable.
  • Accordions use accessible buttons with aria-expanded, smooth transitions and reduced-motion support.
  • Sticky navigation must not create stray borders or lines while scrolling.

12 · Dropdowns, tooltips & modals

  • Overlay z-index values come from the shared layer scale.
  • A higher z-index cannot escape a clipped ancestor; clipping is opt-in on containers that may host overlays.
  • Dropdown triggers manage aria-expanded; Escape closes open menus.
  • Tooltips supplement labels; they never hide essential information.
  • Modals use the browser top layer.

13 · Tables, lists & data

  • Tables prioritize readability and do not draw spreadsheet borders around every cell.
  • Long content truncates only when the column requires it.
  • Tables may scroll horizontally on mobile.
  • Status in dense data remains compact and semantic.

14 · Feedback, loading & empty states

  • Alerts communicate persistent page context; transient results belong to toast-style feedback when that pattern is added.
  • Do not turn every result into success green.
  • Empty states explain what is missing and offer one useful next action.
  • Loading belongs to the component waiting for data rather than blocking the whole page.

15 · Responsive & accessibility

  • Desktop and mobile preserve the same visual language.
  • Grids collapse when appropriate; navigation transforms rather than merely shrinking.
  • Visible focus is never removed.
  • Tabs, accordions and dropdowns expose their state with ARIA.
  • Respect prefers-reduced-motion.

16 · Code hygiene & prohibited patterns

  • No Bootstrap or heavy UI framework unless deliberately approved later.
  • No decorative gradients in the core system. The ruled-note background is the explicit functional line-pattern exception.
  • No reusable inline CSS in product screens.
  • No arbitrary page-specific clones of shared components.
  • No backend, authentication or product business logic inside the UI library.
  • Use Flaticon UIcons consistently for the current icon language.

17 · React migration contract

  • HTML/CSS remains the visual specification until screens are approved.
  • React components map to the approved library rather than inventing a second design system.
  • Props represent deliberate variants that already exist in the contract.
  • The shared system should prevent the “90% consistent, 10% floating” problem by construction.

18 · Final review checklist

  1. Does it reuse an existing component?
  2. Does it use semantic tokens rather than raw values?
  3. Does it align to the correct section/container width?
  4. Are spacing and radius values from the scale?
  5. Do semantic states use the correct meaning and accessible text?
  6. Does it work in light and dark?
  7. Does it remain usable on mobile and keyboard?
  8. Would it still make sense outside this one screen?
