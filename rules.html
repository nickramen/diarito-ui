Rules

Master rules for keeping the Diarito interface consistent as pages, languages, and components grow.

1. General principle

Diarito should feel light, friendly, clear, and consistent. Its identity is built through typography, grid texture, spacing, and a palette where Blue leads, Green is Secondary, Pink is Accent 1, and Purple is Accent 2. Reuse an existing component before creating a new variant.

  • The grid texture is part of the visual identity and is not removed from previews or surfaces where it is already defined.
  • The index uses the defined texture: Blue 300 with Blue 700 lines at 12% alpha and 18px spacing.
  • Reusable classes belong to the namespace .diarito-*.
  • Do not create screen-specific variants when the behavior already exists in another component.

2. Typography

Roboto and Noto Sans KR are the operational UI pair. Englebert and Poor Story are the display pair for identity, short titles, and expressive moments.

  • Body: 0.9375rem, weight 400, line-height 1.5.
  • H1: clamp(1.6rem, 2vw, 2.1rem), weight 500.
  • H2: 1.28rem, weight 500.
  • H3: 1rem, weight 500.
  • Labels: .8rem, weight 500, same base color as titles.
  • Display fonts do not replace long text, inputs, tables, or labels.

3. Color

Brand roles are aliases of the base palette: Primary = Blue, Secondary = Green, Accent 1 = Pink, Accent 2 = Purple, and Neutral = Gray. Official families use 100, 300, 500, and 700.

  • 100 = very soft surface.
  • 300 = contextual background.
  • 500 = main fill.
  • 700 = text, icons, and strong contrast.
  • Success = Green; Info = Blue; Warning = Yellow; Danger = Red.
  • Do not introduce isolated hex values when an equivalent token already exists.

4. Borders & shadows

The interface is flat. Cards, modals, and tables use container borders; inputs, selects, and textareas use the same neutral 1px border as functional form controls. The shell preserves the sidebar right border and topbar bottom border.

  • Buttons, badges, alerts, toasts, tabs, steppers, dropdowns, and pagination use no border. Inputs, selects, and textareas use a neutral 1px border.
  • The sidebar uses a 1px right border and the topbar uses a 1px bottom border as structural layout dividers.
  • No component uses box-shadow, including hover states, modals, or dropdowns.
  • Form controls use a white background, neutral 1px border, and a Blue 1px focus border.
  • Cards, modals, and tables use a thin neutral 1px border.

5. Cards

Cards use a white background, 1px border, medium radius, and no decorative shadow.

  • Header: padding .9rem 1.15rem.
  • Body: padding 1.15rem.
  • Footer: padding 1rem 1.15rem, gap .65rem.
  • Borders between header/body/footer are structural separators, not decoration.
  • In workflows: Exit on the left; Previous + Continue on the right.

6. Buttons

Min-height 2.6rem, padding .58rem .95rem, gap .55rem, and weight 500. Direction icons use arrowLeft and arrowRight.

  • Buttons use no border or shadow.
  • Primary uses Blue 500; hover may move to Blue 700.
  • Filled buttons use white text; never Neutral 950 over brand fills.
  • Secondary uses Green 500.
  • Accent 1 uses Pink and Accent 2 uses Purple.
  • Hover changes the fill without movement or shadow.
  • Icon-only buttons require aria-label.

7. Forms

Inputs, selects, and textareas share minimum height, surface, radius, and focus states.

  • Inputs, selects, and textareas use a white background and neutral 1px border, matching the border language of cards.
  • Visible focus is expressed with a Blue 1px border, never with a shadow.
  • Every control has a visible label and the placeholder does not replace it.
  • Desktop forms normally use two columns and switch to one on mobile.
  • Autocomplete/searchable inputs store the real ID separately from the visible text when applicable.

8. Tabs & steppers

Tabs have no visual hover. Only the normal and selected states matter.

  • .diarito-tabs__list has no padding and has margin-bottom: 1.25rem.
  • Steppers represent progress, not arbitrary navigation.
  • On mobile they may scroll horizontally.

9. Tables & pagination

Tables prioritize readability and do not use spreadsheet-style borders around every cell.

  • Footer: “Showing X of X records”.
  • Pagination uses real arrowLeft / arrowRight icons.
  • Long content is truncated when the column requires it.
  • On mobile the table scrolls horizontally.

10. Feedback

Alerts communicate persistent page context. Toasts communicate the temporary result of an action.

  • Do not turn everything into success.
  • An empty state explains what is missing or why a search returned no results.
  • Loading belongs to the component waiting for data and should not block the whole page when only one section is loading.

11. Prohibited patterns

  • No decorative gradients.
  • No box-shadows in any component.
  • No borders on buttons, badges, alerts, toasts, tabs, steppers, dropdowns, or pagination. Inputs, selects, and textareas are the approved exception with a neutral 1px border.
  • Container borders are reserved for cards, modals, and tables; form controls keep their functional neutral border; sidebar and topbar keep their structural dividers.
  • No border-left-only state accents.
  • No border-bottom-only decoration. The topbar border-bottom is an approved structural divider.
  • No <hr> elements to separate layout sections.
  • No reusable inline CSS.

12. Responsive & accessibility

  • The same visual language is preserved on desktop and mobile.
  • Grids switch to one column when appropriate.
  • The mobile sidebar works as an overlay.
  • Visible focus is never removed.
  • Tabs use roles/aria-selected; modals close with Escape; dropdowns manage aria-expanded; toasts use aria-live.
  • Important information never depends on color alone.

13. Final review

  1. Does it reuse existing components?
  2. Do sizes, weights, and labels match the system?
  3. Do paddings belong to the spacing scale?
  4. Do cards use header/body/footer correctly?
  5. Do states use the correct semantic palette?
  6. Is the grid texture preserved where it belongs?
  7. Do desktop and mobile still clearly feel like Diarito?
  8. Would the component still work visually outside that specific page?
